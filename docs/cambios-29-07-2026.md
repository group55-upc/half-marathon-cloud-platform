## 1. Defectos corregidos

### 1.1. Publicábamos nuestro código fuente en internet

**Dónde:** `frontend/code/angular.json`

El bloque `assets` copiaba **todo** el directorio `src/` a la salida de la
compilación. Resultado: los archivos `.ts`, `.html` y `.css` sin compilar acababan
subidos al bucket de S3, que es público. Cualquiera podía leer, por ejemplo,
`/app/services/race.service.ts`.

```diff
  "assets": [
    {
      "glob": "**/*",
-     "input": "src"
+     "input": "src/images",
+     "output": "images"
    }
  ],
```

No había credenciales dentro, así que no fue una brecha grave, pero era una
configuración incorrecta con exposición innecesaria de información.

**Verificado:** la compilación ya no contiene ningún archivo `.ts`, y ahora **el
pipeline lo comprueba en cada cambio** (ver apartado 3.1). El defecto no puede
reaparecer.

### 1.2. El filtrado numérico de la API no funcionaba

**Dónde:** `backend/code/server.js`

```diff
- paramValues[`:${key}`] = value; isNaN(value) ? value : Number(value);
+ paramValues[`:${key}`] = isNaN(value) ? value : Number(value);
```

Había **dos instrucciones separadas por punto y coma**. La segunda calculaba la
conversión a número y no la guardaba en ningún sitio: el resultado se descartaba.
Los valores numéricos viajaban a DynamoDB como texto, y `"42.195"` nunca coincide
con el número `42.195`.

El defecto estaba **latente**: el dashboard descarga todas las carreras y filtra
en el navegador, así que nadie usaba esa ruta de la API. Solo lo habría notado
quien llamara a la API directamente.

**Verificado:** `GET /races?distance=42.195` devuelve resultados. Antes devolvía
`race not found`.

### 1.3. La caché del compilador estaba versionada

**Dónde:** `.gitignore`, y se retiró del control de versiones
`frontend/code/.angular/`

Es la memoria de trabajo del compilador de Angular, que se regenera sola. Al estar
versionada, cualquier cambio de versión del compilador generaba **decenas de miles
de líneas de diferencias espurias**, enterrando los cambios reales.

Un cambio de dos líneas quedaba oculto entre 52.000 líneas de basura, lo que
hacía imposible revisar nada en GitHub.

> **Aviso para el equipo:** al hacer `pull`, esa carpeta desaparecerá de vuestros
> proyectos. Es inofensivo, se regenera al compilar.

### 1.4. Dependencias muertas en el backend

**Dónde:** `backend/code/package.json` y `package-lock.json`

El backend declaraba dependencias que no usa: `aws-sdk` (la versión 2 completa,
cuando el código usa la 3 modular), `pg` (PostgreSQL, que ya no se utiliza),
`jsonwebtoken` (previsto pero no implementado) y, curiosamente, `npm` e `install`
como dependencias del proyecto.

**Resultado:** el árbol de dependencias pasa de **322 a 118 paquetes**, un 63 %
menos. Imagen de contenedor más pequeña y menos superficie de vulnerabilidades.

## 2. Alta disponibilidad real

**Dónde:** `backend/infra/main.tf`

**El problema.** Teníamos dos tareas del backend, lo que parecía redundancia. Pero
la subred privada solo existía en `us-east-1a`, así que **las dos tareas estaban
en la misma zona de disponibilidad**, es decir en el mismo centro de datos físico.
Si esa zona caía, se caía el servicio completo. El balanceador sí estaba en dos
zonas: teníamos la puerta duplicada y la cocina no.

**El cambio.** Cuatro modificaciones:

```hcl
resource "aws_subnet" "private" {
  count             = length(var.aws-availability-zones)   # <- de 1 a 2 subredes
  availability_zone = var.aws-availability-zones[count.index]
  cidr_block        = cidrsubnet(aws_vpc.vpc.cidr_block, 8, count.index + 2)
  ...
}
```

Y las referencias pasan a `aws_subnet.private[*].id` en la asociación de rutas,
los tres VPC endpoints y el servicio ECS.

**Verificado empíricamente:**

```
| Estado   |     Zona      |
| RUNNING  |  us-east-1a   |
| RUNNING  |  us-east-1b   |
```

Nótese que no le decimos a AWS *"pon una tarea en cada zona"*. Le damos la lista
de subredes y ECS reparte solo. Eso es lo que significa un servicio gestionado:
se declara el resultado deseado, no los pasos.

### El precio, que es el dato interesante

Los VPC endpoints de tipo Interface **se facturan por zona de disponibilidad**,
no por endpoint. Al pasar a dos zonas, los tres endpoints crean seis interfaces de
red en lugar de tres:

| | Antes | Ahora |
|---|---|---|
| VPC endpoints Interface | 0,72 $/día | **1,44 $/día** |
| **Total infraestructura** | **2,40 $/día** | **3,12 $/día** |

**Cumplir la tolerancia al fallo de zona cuesta 0,72 $ al día, un 30 % más.** Y el
sobrecoste no viene del cómputo —Fargate se paga por tarea, da igual dónde esté—
sino íntegramente de un componente de red que no ejecuta ninguna lógica.

Es una consecuencia que no anticipamos al plantear el requisito y que solo
apareció al calcular el precio.

## 3. Integración continua y despliegue

**Dónde:** `.github/workflows/ci.yml` y `.github/workflows/deploy.yml`

Antes había un único archivo que hacía literalmente
`echo "Backend CI will be configured later"`. Se ha eliminado.

### 3.1. `ci.yml` — automático

Se ejecuta **solo**, en cada `push` a `main` y en cada *pull request*. **No
requiere credenciales de AWS**, que es la clave de que funcione siempre. Tres
trabajos en paralelo:

| Trabajo | Comprueba |
|---|---|
| `terraform` | Formato (informativo) y validez de la configuración |
| `frontend` | Que las dependencias instalan y la aplicación compila |
| `backend` | Sintaxis, auditoría de dependencias, construcción de la imagen y análisis con Trivy |

**La parte más útil: una guarda de regresión.** Tras compilar el frontend, el
pipeline cuenta los archivos `.ts` en la salida y **falla si encuentra alguno**. El
defecto del apartado 1.1 ya no puede volver sin que GitHub lo bloquee.

No basta con arreglar un fallo: hay que impedir que reaparezca.

**Y ya demostró su utilidad.** La primera ejecución detectó que el `providers.tf`
exige Terraform `>= 1.10.0` mientras el pipeline instalaba la 1.9.8. Una
incompatibilidad de versiones que el despliegue local nunca habría revelado,
porque cada uno tiene instalada una versión suficiente.

### 3.2. `deploy.yml` — manual

Se lanza desde la pestaña **Actions** del repositorio. Despliega **la aplicación**
sobre una infraestructura existente: publica la imagen en ECR, fuerza el
redespliegue del servicio ECS, espera a que la API responda, compila el frontend
inyectando la dirección del balanceador y lo publica en S3.

Etiqueta la imagen **dos veces**: como `v1.0`, que es la referencia fija de la
definición de tarea, y con el hash abreviado del commit. Esto último nos da
trazabilidad de versiones, que antes no existía.

**Por qué es manual y no continuo.** Dos razones estructurales, y conviene
defenderlas así:

1. **Las credenciales del laboratorio caducan cada pocas horas.** Hoy mismo se nos
   cayó la sesión en mitad del trabajo. Un pipeline que dependiera de ellas
   estaría en rojo la mayor parte del tiempo, y un pipeline permanentemente roto
   deja de aportar información.
2. **El estado de Terraform está en local.** El pipeline no puede gestionar
   infraestructura porque no tiene el inventario de lo que existe. Localiza los
   recursos preguntando a la API de AWS en lugar de leer los `outputs`.

La segunda razón es además una separación de responsabilidades correcta: la
infraestructura se aprovisiona pocas veces, la aplicación se despliega muchas.

Y un argumento que conviene tener a mano: **aprobar los despliegues manualmente es
práctica estándar en producción.** No es un apaño.

**Requisito para usarlo:** configurar en Settings → Secrets and variables →
Actions los secretos `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY` y
`AWS_SESSION_TOKEN`, que hay que actualizar en cada reinicio del laboratorio.

## 4. Escalado automático

**Dónde:** `backend/infra/observability.tf`

**Por qué.** La elasticidad es el concepto central de la computación en la nube y
**no aparecía en el proyecto**: teníamos dos tareas fijas, siempre, pasara lo que
pasara.

**Qué hace.** De 2 a 4 tareas, con objetivo del 70 % de CPU. Se usa *target
tracking*: se declara el valor de CPU deseado y AWS crea y gestiona por su cuenta
las alarmas necesarias para mantenerlo.

**Un detalle deliberado:** los tiempos de espera son asimétricos. Escala hacia
arriba en 60 segundos y hacia abajo en 300. El razonamiento es que quedarse corto
de capacidad degrada el servicio, mientras que tener una tarea de más un rato
cuesta céntimos. Ante la duda, sobra capacidad.

**Coste.** La política es gratuita. Solo se pagan las tareas extra mientras están
activas.

**Verificación:**

```powershell
aws application-autoscaling describe-scalable-targets --service-namespace ecs --output table
```

## 5. Alarmas y avisos

**Dónde:** `backend/infra/observability.tf`

El capítulo de observabilidad de la memoria decía que no había alarmas. Ahora hay
cuatro, dentro de las diez gratuitas por cuenta:

| Alarma | Se dispara cuando |
|---|---|
| `marathon-backend-errores-5xx` | 5 o más errores del servidor en 5 minutos |
| `marathon-tareas-no-sanas` | Alguna tarea no pasa el health check durante 2 minutos |
| `marathon-cpu-alta` | CPU por encima del 85 % durante 10 minutos |
| `marathon-memoria-alta` | Memoria por encima del 85 % durante 10 minutos |

Con el escalado activo, la alarma de CPU no debería dispararse nunca: si lo hace,
significa que se ha alcanzado el máximo de tareas. La de memoria **sí requiere
intervención manual**, porque el escalado configurado no reacciona a la memoria.

**Un detalle que casi todo el mundo configura mal:** `treat_missing_data =
"notBreaching"`. Cuando no hay tráfico, algunas métricas no publican ningún dato.
Sin esa línea, el silencio nocturno se interpretaría como fallo y llegarían
alarmas falsas cada noche.

### Avisos por correo

Las alarmas publican en un tema de SNS, `marathon-alertas`, con **suscripción para
los seis integrantes del equipo**.

> **Acción requerida de cada uno:** habréis recibido un correo de AWS con asunto
> *"AWS Notification - Subscription Confirmation"*. **Hay que pulsar el enlace
> `Confirm subscription`.** Tiene toda la pinta de spam, pero quien no lo confirme
> no recibirá ninguna alarma.

## 6. Importación periódica de carreras

**Dónde:** `backend/infra/lambda.tf`, `lambdas/import-races/index.mjs`,
`lambdas/import-races/README.md`, `lambdas/import-races/ejemplo-races.json`

Estaba en el planteamiento inicial como funcionalidad opcional, y la carpeta
`lambdas/import-races/` llevaba todo el proyecto vacía. **Ya está implementada.**

```
EventBridge (lunes 06:00 UTC)
      |
      v
   Lambda  --lee-->  S3 (imports/races.json)
      |
      +-----------> DynamoDB (inserta solo las nuevas)
      |
      +-----------> SNS (resumen por correo)
```

**Diferencias respecto al diseño inicial**, que preveía un CSV disparado por un
evento de S3 hacia RDS: el formato es JSON, el disparador es una programación en
lugar de un evento, y el destino es DynamoDB. Se eligió una programación periódica
porque la importación es un proceso de sincronización, no una reacción a la subida
de un fichero.

### Lo importante del diseño: idempotencia

Dos carreras se consideran la misma si coinciden **nombre y fecha**. La función
puede ejecutarse mil veces sin duplicar nada.

Es imprescindible en un proceso automático que nadie supervisa: si EventBridge
reintenta una invocación, o si alguien la lanza a mano para probar, el resultado
debe ser idéntico.

**Demostrado en dos ejecuciones seguidas:**

```
1ª vez:  {"ok":true,"importadas":5,"duplicadas":0,"invalidas":0}
2ª vez:  {"ok":true,"importadas":0,"duplicadas":5,"invalidas":0}
```

### Decisión de arquitectura: la función corre FUERA de la VPC

Ubicarla en la subred privada obligaría a añadir VPC endpoints de tipo Interface
para SNS y para Lambda, con su coste por hora y por zona. Fuera de la VPC alcanza
S3, DynamoDB y SNS por sus interfaces públicas usando las credenciales del rol,
sin coste adicional de red.

El compromiso es aceptable porque **no accede a ningún recurso privado**, solo a
servicios gestionados. El backend, que sí es accesible desde internet y por tanto
necesita aislamiento, permanece en la subred privada.

### Validación

Se descartan los registros sin nombre, ciudad, país, fecha en formato
`AAAA-MM-DD` o distancia numérica positiva. Los descartados se enumeran en el
resumen por correo.

Nótese que **esta validación es más estricta que la de la propia API**, que no
valida el cuerpo de las peticiones. Es una incoherencia conocida, recogida en el
análisis de seguridad de la memoria.

### Cómo probarla

```powershell
aws s3 cp lambdas/import-races/ejemplo-races.json s3://marathon-cloudupc-website/imports/races.json
aws lambda invoke --function-name marathon-import-races respuesta.json
Get-Content respuesta.json
```

## 7. Automatización del despliegue

**Dónde:** `deploy.ps1` (raíz del repositorio)

Un script que ejecuta las **ocho fases** del despliegue completo desde cero:
verificación de herramientas, verificación de credenciales, infraestructura base,
imagen Docker, servicio ECS, espera activa a que el backend responda, frontend, y
datos de ejemplo.

| | Primer despliegue | Redespliegue |
|---|---|---|
| Duración medida | ~12 min | **2,2 min** |

**Características:**

- **Verifica antes de crear.** Un problema de configuración se detecta en segundos
  en lugar de a mitad del despliegue.
- **Resuelve el orden de las dos fases.** El error `CannotPullContainerError` que
  sufrimos el primer día no puede repetirse: sube la imagen a ECR *antes* de crear
  el servicio.
- **Espera activa.** Sondea el balanceador cada 15 segundos hasta que responde,
  antes de publicar el frontend.
- **Inyecta la URL del balanceador** en el código del frontend automáticamente.
- **Verifica la compilación** antes de subirla a S3.
- **Fallo seguro.** Si aborta, no destruye lo ya creado.

### Por qué esto importa más de lo que parece

**La capacidad de recrear el entorno en dos minutos es lo que hace viable
destruirlo cada día.** Un entorno cuya recreación costara una tarde no se
destruiría nunca: se dejaría encendido por comodidad y agotaría el crédito.

La automatización no es solo eficiencia, es **la condición que permite una
disciplina de control de coste** que de otro modo no se sostendría.

**Dónde:** `database/seed-races.ps1`

Carga doce carreras mediante peticiones a la API. Es el equivalente funcional del
`database/seed.sql`, que quedó inservible al cambiar a DynamoDB.

## 9. Amazon Bedrock: por qué no está

Se evaluó incorporar el asistente conversacional previsto como opcional. Se
descartó, y la investigación tiene **tres niveles**:

**1. Nuestro usuario no tiene permiso.** Listar los modelos devuelve acceso
denegado, con el mensaje *"no identity-based policy allows"*. Conviene el matiz: no
está prohibido explícitamente, es que el permiso nunca se concedió. Bedrock no
forma parte de los servicios habilitados del laboratorio.

**2. No podemos auditar el rol del backend.** El backend corre con `LabRole`, cuyos
permisos podrían diferir. Sus políticas: cuatro gestionadas de AWS, ninguna con
Bedrock, y tres propias del laboratorio **cuyo contenido no podemos leer**, porque
`iam:GetPolicy` está denegado explícitamente.

**3. Y hay un obstáculo arquitectónico, independiente de los permisos.** Nuestras
tareas están en una subred privada sin salida a internet, y Bedrock —a diferencia
de S3 y DynamoDB— **no tiene endpoint de tipo Gateway**, que son los gratuitos.
Integrarlo exigiría un endpoint de tipo Interface: 0,48 $/día, un 15 % más de
factura.

De ahí una consecuencia metodológica: **tampoco hay una prueba barata.** Desde la
subred privada la llamada moriría por tiempo de espera de red, y no podríamos
distinguir si es por falta de permiso o por falta de ruta.

**Cómo presentarlo:** no es "no nos dio tiempo". Es "investigamos en tres niveles,
determinamos que el entorno no lo permite, calculamos cuánto habría costado y
dejamos documentado el diseño de lo que se habría construido".

Está en `docs/architecture.md` apartado 9, y en la memoria apartado 5.5.

## 10. HTTPS: verificado que no es posible

La ausencia de cifrado sigue siendo la limitación más grave. Hoy se han comprobado
**las dos vías posibles**:

| Vía | Resultado |
|---|---|
| Certificado de ACM en el balanceador | **ACM está disponible**, pero emitir un certificado exige acreditar un dominio propio |
| CloudFront delante del bucket | **Denegado en el laboratorio.** Era la opción que daba HTTPS sin dominio |

Ya no es "no supimos cómo": es "probamos las dos rutas y ninguna está a nuestro
alcance en este entorno".

Y hay que entender que las dos mitades están acopladas: servir el frontend por
HTTPS sin hacer lo mismo con la API haría que el navegador bloqueara todas las
llamadas por política de contenido mixto. Resultado: una web que carga bonita y no
funciona. Por eso también se descartó Amplify, que sirve solo por HTTPS.

## 11. Privacidad y buenas prácticas

### Correos del equipo fuera del repositorio

**Dónde:** `backend/infra/terraform.tfvars.example` (versionado) y
`backend/infra/terraform.tfvars` (en el `.gitignore`)

Las direcciones de correo para las alarmas **no van en un archivo versionado**.
Cuatro de las seis son direcciones personales, y dejarlas en el repositorio las
expone a cualquiera con acceso y a los rastreadores de spam que recorren GitHub
sistemáticamente. Datos personales de terceros no van en el control de versiones.

Es el mismo patrón que Miquel ya usaba con su `terraform.tfvars.example`.

Para desplegar, cada uno copia la plantilla y pone lo suyo:

```powershell
Copy-Item terraform.tfvars.example terraform.tfvars
```

### El lock de Terraform pasa a versionarse

**Dónde:** `.gitignore`

`.terraform.lock.hcl` fija las versiones exactas de los proveedores y sus huellas
criptográficas. Terraform recomienda versionarlo, y lo avisa cada vez que cambia.

Sin él, cada integrante puede acabar con una versión distinta del proveedor de
AWS, y un `apply` que funciona en un equipo puede fallar en otro. Es el mismo
argumento que aplicamos al `package-lock.json`, que también estaba excluido y
ahora se versiona.

## Lo que queda pendiente, y requiere decisión del equipo

Ninguno de estos puntos estaba al alcance de una sesión: **todos requieren o un
acuerdo del grupo o un redespliegue coordinado.** El detalle completo, con código
y esfuerzo estimado, está en `docs/mejoras-propuestas.md`.

### 1. La URL del backend sigue dentro del código

`frontend/code/src/app/services/race.service.ts` tiene la dirección del
balanceador escrita dentro, y esa dirección **cambia en cada `terraform destroy` +
`apply`**. Nos ha roto la web dos veces.

**Solución:** un `config.json` que el frontend lea al arrancar, en lugar de
compilar la dirección dentro. Es el principio de **separar configuración de
código**. Ahora mismo el `deploy.ps1` y el pipeline la inyectan automáticamente,
así que el problema no molesta — y eso tiene un riesgo: los problemas que no
molestan no se arreglan nunca.

**Esfuerzo:** 1-2 horas. Toca código compartido, por eso lo propongo en lugar de
hacerlo.

### 2. El nombre del bucket impide trabajar en paralelo

`marathon-cloudupc-website` está fijado en el código, y **los nombres de bucket de
S3 son únicos en todo el mundo**, no por cuenta. Se comportan como un dominio, no
como un nombre de carpeta.

**Consecuencia: solo una persona puede tener la infraestructura desplegada a la
vez.** Al segundo le fallará con `BucketAlreadyExists`.

**Solución:** añadir el identificador de cuenta al nombre, cuatro líneas.

**Contrapartida:** obliga a destruir y recrear el bucket, y la URL de la web
cambia. Requiere un redespliegue coordinado.

### 3. El despliegue en dos fases sigue siendo un truco

La variable `enable-ECS` fuerza manualmente un orden que Terraform debería
deducir. Lo limpio serían **dos estados de Terraform separados**, uno para la
infraestructura base y otro para la aplicación. Es la práctica habitual en
producción.

**Esfuerzo:** media jornada.

### 4. Decidir si filtramos en cliente o en servidor

El frontend descarga todas las carreras y filtra en el navegador. Con 17 carreras
es irrelevante; con 10.000 la web se arrastra. Los filtros del backend existen y
no se usan.

Hay que **decidirlo y documentarlo**, en un sentido o en otro. Y si se opta por el
servidor, harían falta índices secundarios en DynamoDB, porque el filtrado actual
recorre la tabla completa.

### 5. No hay pruebas automatizadas

`vitest` está instalado en el frontend y existe un archivo de especificación
vacío. Con dos o tres pruebas reales ejecutándose en el pipeline, la percepción
del proyecto cambia.

**Esfuerzo:** bajo. Es probablemente el punto pendiente con mejor relación entre
esfuerzo y valor.

### 6. Confirmar con el profesor que desviarse está permitido

Usamos DynamoDB y ECS Fargate en lugar de RDS y EKS. Si el enunciado los pedía
explícitamente, *"usamos otros servicios para aprender más"* puede leerse como no
haber cumplido los requisitos.

**Merece preguntarlo antes de entregar, no después.**

## Acuerdos operativos que propongo

**1. Destruir la infraestructura ANTES de terminar la sesión, no después.**

Hoy se nos cayó el laboratorio con la infraestructura encendida, y perdimos el
acceso para pararla. Cerrar la sesión no detiene el gasto, pero sí quita la
capacidad de detenerlo.

```powershell
cd backend\infra
terraform destroy
```

**2. Coordinar quién despliega.** Cuesta 3,12 $/día y solo uno puede a la vez por
el nombre del bucket.

**3. Actualizar las credenciales en `~/.aws/credentials`, no como variables de
entorno.** Así cualquier ventana de PowerShell las coge y solo hay que pegarlas en
un sitio.

**4. Confirmar la suscripción de SNS** cuando llegue el correo de AWS.

**5. Antes de comitear, `git status` y revisar la zona verde.** El repositorio
marca decenas de archivos como modificados por el ruido de finales de línea de
Windows. Nunca `git add .`.

## Cómo comprobarlo todo

```powershell
# URLs del despliegue
cd backend\infra ; terraform output ; cd ..\..

# La API responde y alcanza la base de datos
Invoke-RestMethod "http://<alb>/"
Invoke-RestMethod "http://<alb>/connection"

# El filtro numérico corregido
Invoke-RestMethod "http://<alb>/races?distance=42.195"

# Las tareas están en dos zonas
$t = (aws ecs list-tasks --cluster marathon-cluster --service-name marathon-service --query "taskArns[]" --output text) -split "\s+"
aws ecs describe-tasks --cluster marathon-cluster --tasks $t --query "tasks[].{Zona:availabilityZone,Estado:lastStatus}" --output table

# El escalado automático está configurado
aws application-autoscaling describe-scalable-targets --service-namespace ecs --output table

# Las alarmas existen
aws cloudwatch describe-alarms --alarm-name-prefix marathon --query "MetricAlarms[].{Alarma:AlarmName,Estado:StateValue}" --output table

# La Lambda funciona y es idempotente
aws lambda invoke --function-name marathon-import-races respuesta.json ; Get-Content respuesta.json

# El pipeline de CI
# -> pestaña Actions del repositorio en GitHub
```
